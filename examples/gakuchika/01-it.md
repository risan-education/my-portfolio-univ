# IT・情報通信のガクチカ例

想定職種: **システムエンジニア**

## この業種・職種で意識したい経験

この職種を想定するなら、**利用者の困りごとを聞く → 自分の機能案を疑う → 小さく試作する → 操作を観察する → 仕様を修正する**経験が話しやすいです。

## 修正前のガクチカ

> 私が力を入れたのは、サークルの予定を探しやすくする仕組みの試作です。連絡が複数の投稿に分かれ、私自身も集合場所を探し直した経験から、3人の制作班に加わりました。私は利用者への聞き取りと画面案、操作確認を担当しました。5人に聞くと、情報の量より開催日と場所の見つけにくさが課題でした。そこで機能を増やす案を見直し、この2項目を先頭に置きました。試作版では1人が入力場所に迷ったため、ボタンの文言も修正しました。再確認では5人全員が練習用の予定を登録できましたが、同じ人の再試行であり、広く使えるかは未確認です。この経験から、自分の想定で機能を決めず、利用者の操作を見て課題を捉え直す大切さを学びました。

## 何を改善したか

修正前でも利用者への聞き取りはありますが、「便利な機能を増やす」という最初の考えを捨てた場面が弱めでした。改善版では、5人への聞き取りから問題を「情報量」ではなく「日付と場所が見つからないこと」と捉え直し、機能追加をやめた判断を中心にします。

## 改善版ガクチカ

> サークルの予定を探しやすくする仕組みを3人で試作しました。私は当初、機能を増やせば便利になると考えていましたが、利用者5人に聞くと、不満は情報量ではなく「開催日と場所がすぐ見つからないこと」に集中していました。そこで機能追加をやめ、この2項目を画面の先頭に置く案へ変更しました。試作版を操作してもらうと1人が入力場所で迷ったため、説明を足すのではなくボタンの文言を変更しました。再確認では5人全員が練習用予定を登録できました。一方、同じ5人での再試行なので広く使えるとはまだ言えません。自分が作りたい機能から考えるのではなく、利用者の行動を観察して課題そのものを定義し直すことを学びました。

## この例の強いところ

制作物の規模ではなく、利用者の行動を見て課題を再定義しています。改善後も同じ5人での確認にすぎないという限界を残しています。

## これから経験を作るなら：課題設定10例

| 課題 | おすすめする理由 |
| --- | --- |
| サークル予定管理を改善する | 身近な利用者から継続的に反応を得られる |
| 研究室予約を改善する | 利用者と管理者双方の要件を考えられる |
| 学習記録ツールを作る | 継続率を指標にできる |
| 忘れ物共有を改善する | 情報入力と検索の両方を考えられる |
| 学内混雑を可視化する | データ取得と表示価値を検証できる |
| フォーム入力を改善する | 離脱地点を観察できる |
| アクセシビリティを改善する | 異なる利用者の操作を観察できる |
| 検索UIを改善する | 所要時間や成功率を測れる |
| 小規模Webサービスを作る | 短期間で試作と改善を回せる |
| OSSの小さな改善をする | 他者の要件とコードを理解する経験になる |

## 進め方

最初に3〜5人へ困りごとを聞き、作る前に「何ができれば改善と言えるか」を決めます。試作品は説明せず操作してもらい、止まった場所や使わなかった機能を記録します。機能数ではなく、利用者を見て何を捨てたかを残します。

## 面接で深掘りしたい質問

1. 最初はなぜ機能を増やそうと考えたのですか。
2. 5人への聞き取りで最も意外だったことは何ですか。
3. 日付と場所を先頭に置いた理由は何ですか。
4. 同じ5人での再確認にはどんな限界がありますか。
5. 次に別の利用者へ試すなら何を測りますか。
