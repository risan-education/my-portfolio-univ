# Googleを想定したガクチカ例

想定職種: **ソフトウェアエンジニア**

企業研究: [令和就活ラボ・Google](https://risan.jpn.org/?p=13342) ／ 基本例: [IT・情報通信](../01-it.md)

## この会社・職種で意識したい経験

ソフトウェアエンジニアを想定するなら、**作る → 実際に使ってもらう → 利用者の行動を測る → 自分の仕様を捨てて作り直す**経験が話しやすいです。技術の難しさだけでなく、「誰のどんな問題を解くのか」「成功を何で測るのか」まで説明できる経験を選びます。

## 修正前のガクチカ

> 授業のチーム開発で、図書館の座席の空き状況を共有するアプリを、使われる形に作り直すことに力を入れました。実装担当の私は最初、座席番号と空き時刻を入力する設計にしましたが、利用者テストでは知人五人のうち継続して使った人がいませんでした。理由を聞くと、入力が面倒で、自分が得をする前に手間がかかるためでした。そこでチームで、一人が一日に一回は開くことを目標とし、入力を座席のエリアを一タップで選ぶ形に減らしました。二週間の再テストでは開く回数は増えましたが、試験期間が終わると使われなくなりました。

## 何を改善したか

修正前は改善の流れができていますが、「入力を減らした」という機能変更に目が向きやすい文章でした。改善版では、最も重要な転換点を**自分が作った仕様を5人とも継続利用しなかったこと**に置きました。そこから利用者に理由を聞き、成功指標を決め、仕様を削った流れを明確にしています。試験期間終了後に使われなくなった結果も残し、次の仮説につなげました。

## 改善版ガクチカ

> 授業のチーム開発で、図書館の座席共有アプリを使われる形に作り直しました。私は実装担当として座席番号と空き時刻を入力する設計を作りましたが、知人5人の利用テストでは継続利用がゼロでした。機能不足ではなく入力負担が原因ではないかと考えて理由を聞くと、「自分が得をする前に入力が面倒」という声がありました。そこでチームで成功指標を「1日1回開く人の数」と決め、入力をエリアの1タップ選択まで減らしました。2週間の再テストでは利用回数が増えましたが、試験終了後には使われなくなりました。そこで混雑期だけ価値が高いという仮説を残し、次は対象時期を絞る案を提案しました。この経験から、作りたい機能ではなく利用者の行動を測って仕様を変えることを学びました。

## この例の強いところ

「アプリを作った」という制作実績ではなく、**誰にも継続利用されなかった失敗から仕様を変えたこと**が中心です。成功指標を決めて再テストし、その後また使われなくなった結果まで残しているため、プロダクト改善の思考を深掘りできます。

## これから経験を作るなら：課題設定10例

| 課題 | おすすめする理由 |
| --- | --- |
| 学内の小さな不便を解くWebアプリを作る | 利用者を見つけやすく、試作と改善を繰り返せる |
| サークル予定管理を改善する | 実際の利用頻度を測れる |
| 研究室予約UIを改善する | 利用者と運営者双方の要件を考えられる |
| 学習記録アプリを試作する | 継続率を指標にできる |
| 大学施設の混雑を可視化する | データ取得と利用価値を考えられる |
| フォームの入力離脱を減らす | UI変更の前後を比較しやすい |
| アクセシビリティを改善する | 多様な利用者の行動を観察できる |
| 検索機能を改善する | 成功率や所要時間を測れる |
| OSSの小さなIssueを解決する | 他者のコードと要件を理解する経験になる |
| データ可視化ツールを作る | 意思決定に役立つかまで検証できる |

## 進め方

最初から大きなサービスを作らず、実際に困っている人を3〜5人見つけます。作る前に「何ができれば改善と言えるか」を一つ決めます。

試作品は早く見せ、説明せずに操作してもらいます。止まった場所、使わなかった機能、継続しなかった理由を記録します。コード量や機能数ではなく、**利用者の反応を受けて何を削り、何を残したか**をポートフォリオに残します。

## 面接で深掘りしたい質問

1. 最初の設計で、どんな利用者行動を想定していましたか。
2. なぜ「機能不足」ではなく「入力負担」を疑ったのですか。
3. 成功指標を「1日1回開く人」にした理由は何ですか。
4. 試験期間後に使われなくなった結果から、何を学びましたか。
5. もう一度作るなら、コードを書く前に何を確かめますか。
